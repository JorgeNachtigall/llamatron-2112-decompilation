# Deliberate deviations from the original

Every place where the port knowingly differs from the 1992 original. Each entry says why and who owns it.

| # | Area | Original behaviour | Port behaviour | Why | Owner |
|---|------|--------------------|----------------|-----|-------|
| 1 | llatron.spl sample 30 | Sample runs 96 bytes past the end of the file (the driver plays whatever follows in memory) | Padded with silence | The bytes past EOF are undefined | W1 |
| 2 | f.cmp last glyph (chars 7D-7F) | Glyph is truncated; its missing rows come from DGROUP 409C+ (the hi-score table) | Missing rows padded blank | The original shows hi-score bytes as pixels; that is a bug, not data | W1 |
| 3 | Text on a page target (W6, text.c) | Glyph cells past the page end are written into the gap after the page and, beyond ~4.8 rows, into the next page | Cells past the page end are dropped | No caller reaches it: the HUD and hi-score text are ported and diff-tested, and tests/oracle/level_sweep.py checks every level for dropped cells (draw_drop_stats) | W6 |
| 4 | Keyboard taps (W2, engine/input.c, apps/llamatron_main.c) | INT 09 runs asynchronously, so any real key press overlaps at least one timer tick, and its make code is the last scan code ([587]) for a frame or more | A key released before the next timer tick stays held until that tick (fire is read there, 1000:3e12; the tick runs in every game state), never longer. In the game the shell also holds a break back until a game frame has run with its make, so frame-side readers (frame read 1e7b:0000, the scrollers' last-scan-code skip 1000:58a4) see the press too | Host events arrive in batches; press + release in one batch (a fast tap; keydown + keyup in one rAF on the web) would otherwise be lost. Presses that span a tick and a frame behave exactly as the original; a tap is never still down at a later check (a Space that skips the start-up scroller does not also start a game). Tests: engine_selftest, llamatron_tap, web_llamatron_tap | W2 |
| 5 | Sound DMA page split (W2, engine/snd.c) | A sample crossing a 64 KB DMA page is played in two transfers; the second is started from the IRQ handler (sblaster.bin 0x511), leaving a gap of microseconds | Played as one continuous block; end time = length / rate | The gap is far below one tick and inaudible; status timing is unaffected at tick resolution | W2 |
| 6 | Title sound on the web (W2, apps/title_main.c) | fs.exe requests sample 1Bh right after showing the picture | On the web the request waits until the browser's AudioContext runs (first click); natively and in test runs it is immediate | Browsers keep audio suspended until a user gesture and SDL silently drains the queue meanwhile, so the sound would otherwise never be heard | W2 |
| 7 | (withdrawn) Scroller canvas (W6, draw_scroller.c) | Not a deviation: scroller_start clears VRAM from 1F40 to the end of the 64 KB plane, gaps included (vram_clear_from_1f40, 1000:5862 -> 6383), as draw_scroller.c's canvas_clear does | Same | Number kept so later rows keep theirs | W6 |
| 8 | Entity slot searches (W5a) | Searches in enemy_init_10, the debris search and the rock search run past the 70-slot table without bound (debris/rock only with kill action 04's inherited DX=0x60). Kill action 03's ten rocks (1000:212d) check for the table end only after a busy slot (2137..213f), so when the last slot (69) takes a rock the loop goes on past the table, writes the rest of the rocks wherever a negative word starts a 0x40 record (DS:5A41.. is zero, so in play that is the shot records 68C9.. or the random table 6AC9..), and reads two or more random numbers per extra rock | Searches stop at the table end; with the walker past the table, the drop keeps the shot direction; no rocks or random reads past the table | Past the table is unrelated memory. Pinned in tests/oracle/test_w5a_deviations.py (test_snake_init_full_table, test_kill_search_full_table: slots 0..69 match, only the records past the table, the counters, the snake trail, the drop and, for kill action 03 with slot 69 free, the random index differ) | W5a |
| 9 | enemy_shot_alloc with no free slot (W5a) | Callers write +3a of the nonexistent record 70 | The write is dropped | Writes past the entity table. Pinned in tests/oracle/test_w5a_deviations.py (test_fire_back_no_free_slot: ent_hit_04/05 on a full table match apart from record 70; test_shot_alloc_no_free_slot: NULL, nothing changed) | W5a |
| 10 | P2 trail start (W4, tick.c, 1000:199d) | The loaded image has [2CF9] = 2 (not entry-aligned), and nothing resets it before P2's first trail write, so the same-position compare reads a misaligned entry | The compare uses entry 0 | At most a one-tick difference for P2, and only if those bytes equal P2's ship position | W4 |
| 11 | think_08 hunter search (W5b, 1000:4a22) | The search adds the slot number, not slot*64, so only a slot-0 llama is found (this part is reproduced). When the stray byte at table+slot is 5, it homes in on a misaligned record and later writes into it | That misaligned homing and its writes are not reproduced | It needs raw byte views of the entity table (§0.1); rare and data-dependent | W5b |
| 12 | Llama searches (W5b, herder_claim_llama 1000:3a17 and think_08 1000:498e) | Both scans (3a24 / 499b) run until they have seen g_unhatched (091B) type-5 records, past the end of the entity table when fewer type-5 records exist than unhatched | Stops at the table end | Same rule as #8 | W5b |
| 13 | rescue_level_flags shift (W5b) | SAR by loop_count: an 8086 uses the full count, a 286+ masks it to 5 bits | Count mod 32 (286+/DOSBox behaviour) | Reference runs use DOSBox; only matters after 32+ loops | W5b |
| 14 | Follower trail read (W5b, 1000:194f) | Reads trail[head + follower_lag] unmasked; the overflow into P2's ring is reproduced, but past the end of P2's ring it reads whatever follows in DGROUP | Past the end of P2's ring the read wraps to P1's start | Needs about 25+ llamas in one wave with the head near the end; the memory beyond is unrelated | W5b |
| 15 | Droid recount (W5b, 1000:17ef) | Counts over the 4 records past the entity table (slots 70..73) | Treats those slots as free (entities_clear frees them) | Differs only if something writes those records | W5b |
| 16 | anim 04 on page-0 frames (W6, entities/anim.c, 1000:4646) | Its plain draw goes through sprite_draw_core, which does not preserve DI, and then anim 05 reads "the entity" through that DI: on frames drawn into page 0 (where the plain draw is not clipped away, see the x slip below) the scaled draw uses whatever DGROUP bytes the blitter's last VRAM address points at | The scaled draw uses the entity, as it does on page-1 frames | Reads unrelated memory at a VRAM-derived address; anim 04 lasts one frame (it moves on to anim 05). The x slip itself (the plain draw lands at x = [0x39d3], i.e. 0 or 0x2000) is reproduced | W6 |
| 17 | Entity draws below the page (W6, entities/anim.c) | The scaled draw always draws its first row and the horizontal beam takes any row of the 1638-row tbl_row_offset (DS:2D07, 1000:4795..4800), so an entity below row 199 writes into the gap after the page and on into the next page | Cells past the page end are dropped (as #3) | Entities using those anims stay on the playfield (tests/oracle/level_sweep.py: no dropped cells on any level); nothing on screen depends on it | W6 |
| 18 | sprite_draw_to_bg (W6, draw_sprite.c draw_sprite_with_background, 1000:4bd3) | Loads the page offsets 0x4000 and then [0x39d3] into AX, the blitter's x, before its two draws, so the caller's x is never used | Both draws are at the caller's x (tests/oracle/test_draw_wrappers.py runs the original's instructions with AX put back, and checks that the whole routine ignores x) | The routine has no caller in game86; the helper is for the port's own use | W6 |
| 19 | Bouncing shot reflection (W5a, bullets.c, 1000:0c8f) | The search for the shot's (direction, vx, vy) runs on past the 16 control-table entries, up to 0x6f of them, through the next tables. A match there (or in the bounce table) gives an index into whatever follows | A shot that no entry matches dies at the edge, as it does when the search runs out | player_fire and the droid only give shots table triples, and direction 0 (set by some hit handlers) never matches. Also: an entity whose sprite number has no frame has a y reach of 8 (the original reads header bytes through a link entry), and a hit handler index of 18 or more is not called Pinned in tests/oracle/test_w5a_deviations.py (test_bounce_reachable_triples: every table triple, and each with direction 0, bounced at every edge, matches the original) | W5a |
| 20 | Transition timing in replays (W3, tests/replay/compare.py) | Some transitions cost the original real CPU time inside a frame: the title redraw and page copies around death/continue (death_continue), the game-over and hi-score screens (game_over_hiscore) and the warp banner/box and wave background (warp). Timer IRQs keep firing meanwhile, so the next tick/draw hook switch lands one tick earlier or later relative to the frames | The port does the same work in zero time; a switch happens on the frame count alone | A frame/tick count can't reproduce CPU time. The replay report lists a one-tick shift at a tick/draw hook switch as "timing" when the bytes equal the port's state one tick later/earlier; it doesn't count as the first divergence. Start-up offsets are calibrated per scenario (tick_phase / start_delay in tests/dosbox/test_reference_golden.py), these transitions can't be | W3 |
| 21 | Snake trail index (W5b, entities/think_snake.c think_1d, 1000:36a0) | The head stores its position at trail entry vx (DS:4481 + 8 * vx) without masking; a vx outside 0..63 writes outside the 64-entry trail (negative: onto the score digits at 4441) | The entry is vx mod 64 | Unreachable in play: enemy_init_10 (2def) is the only maker of a snake head, with vx = 0, and think_1d itself is the only later writer, keeping it 0..63 ((vx + 1) & 63; hit 08/06 and the homing mover don't touch vx; checked with Thorn). Only random test state gets there, so tests building a think 0x1d head give it vx 0..63 | W5b |
| 22 | Launcher and llama.inf (W1; llama.exe 1000:01e7, 0449, 0103) | A missing or invalid llama.inf ([0]/[2]/[4], upper-cased, not V/E, J/K, A/S/R/N) stops the launcher with "No or Invalid Game Configuration found - Please run 'Install'". A/S/R make it detect the card (AdLib at 388h, MPU-401, Sound Blaster OPL at 228h) and load adlib.bin/roland.bin/sblaster.bin, exiting with "Selected Sound Card not found" if it is missing. A cpu digit other than 0 runs game386.exe (not shipped). A file under 9 bytes is read with zeros after it | No launcher: an invalid file gives the shipped settings ("V K N 0 N"); the extractor's config.dat import marks it absent. Short files read as zeros after their end, as in the launcher. Any sound type but N plays the Sound Blaster samples through the port's mixer, with no detection. The cpu digit is kept but the game is always game86 | There is no DOS hardware to detect and only the Sound Blaster driver and samples are ported (this release's installer writes only S or N; A and R are registered-version options). Refusing to start would only lock the player out; the options can be fixed with the command line. Tests: ctest extract_launcher_oracle, settings_parse_oracle | W1 |
| 23 | Options screen (W1, src/options, PLAN M7) | The game's options live only in llama.inf, which install.exe's text-mode menus write (1000:050f) and the launcher reads at start (llama.exe 1000:01e7); changing them means leaving the game and running Install | F2 on the title opens a port-side screen, drawn with the game's font and palette, that edits exactly llama.inf's fields (video V/E, control K/J, sound S/A/R/N, processor digit, flashes Y/P/N). Enter stores them through settings_format_inf in the host's llama.inf (pref dir / web IDBFS) and applies them: video and control at once (the title picture is reloaded for the new adapter), the rest when the game starts. Esc or F2 leaves without changes. F2 no longer starts the game from the title (any other character key still does) | There is no DOS installer in the port. The screen keeps llama.inf's meaning and file format, so files stay exchangeable with the original. Its wording is the port's own, and the game's code paths never see it (it exists only before game_init). Tests: options_selftest, llamatron_options_* | W1 |
| 24 | Ticks only at frame boundaries (W2, engine/timing.c, apps/llamatron_main.c; PLAN.md §2.4) | The timer interrupt (INT 08, 1000:3de4: sound driver tick, then the game's tick hook) pre-empts the main loop wherever it is, also in the middle of a frame's drawing | Each emulated retrace runs its due timer ticks first, then one game frame (the order of frame_run 1e7b:013f around its vsync wait 1000:e5f3); a tick never splits a frame | emscripten_set_main_loop has no interrupts and no threads; the tick logic does not read what the draw code writes mid-frame, so game state is the same and at most which frame shows a state moves by one. The replay side's timing differences are #20. Tests: engine_selftest, whole-game lockstep (tests/oracle/whole_game.py, same schedule both sides), llamatron_visual_walk_vga | W2 |
| 25 | Catch-up cap after a host stall (W2, engine/timing.c timing_retraces_due, apps/llamatron_main.c MAX_RETRACES_PER_HOST_FRAME) | INT 08 never loses a tick: after a long frame (disk access, a slow redraw) every tick that came due has run, so the game "catches up" | Wall-clock play runs at most 4 emulated retraces (with their ticks) per host frame and drops the rest of the backlog (RetraceClock.dropped_retraces) | A host stall (window dragged, tab in the background, the machine asleep) would otherwise fast-forward the game by seconds or minutes in one go; ordinary 60/120 Hz frames need 1-2 retraces and never hit the cap. Test runs and replays take one retrace per frame and are unaffected. Test: engine_selftest (retrace clock: no drops at 60 / 120 Hz, a 3 s stall runs 4 and drops the rest) | W2 |
| 26 | Herder llama mode (W5b, entities/think_herders.c herder_handle_llama, 1000:3aeb) | What a herder does with a llama it reached jumps through the 4-entry table at CS:3AFF indexed by the herder's +20 (sub_mode). enemy_init_18/26 set it to 2/3, but enemy_init_04 (1f96, a herder hatching from think 07) leaves +20 as the slot's previous occupant left it (0 in fresh memory, init01_mode from kind 1, but also e.g. 0x800 from a snake head, 0x200 from hit 0a (2da7), coordinates, or title-llama residue in slots 0..8). Outside 0..3 the jump goes to an address read from the code after the table (CS:3B07 on: 06C7, 21C6, 000A, ...), mid-instruction | An unknown mode does nothing: the herder stays on the llama and tries again each step | Reachable (kind 04 spawns with llamas in 16 of the 100 levels, from level 2) but needs a leftover +20 above 3; jumping into arbitrary code is not something to reproduce (§0.1) | W5b |
